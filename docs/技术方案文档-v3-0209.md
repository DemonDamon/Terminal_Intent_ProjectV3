## 1. 方案概述

### 1.1 项目背景

广东移动终端商城需要一套智能化的用户购买意向预测系统，通过分析用户行为数据，识别高购买意向客户，支撑精准营销业务。

### 1.2 技术目标

| 目标 | 描述 | 量化指标 |
|------|------|----------|
| **预测准确性** | 模型能够有效区分高低意向用户 | AUC ≥ 0.75, F1 ≥ 0.6 |
| **服务可用性** | API服务稳定可靠 | 可用性 ≥ 99.9% |
| **响应性能** | 满足在线预测时效要求 | P95 ≤ 5s (1000条) |
| **可维护性** | 支持模型迭代和热更新 | 无需重启服务 |
| **可部署性** | 支持离线环境部署 | Docker镜像离线导入 |

### 1.3 技术约束

| 约束项 | 说明 |
|--------|------|
| Python版本 | 3.10（与现有环境一致） |
| 部署环境 | 离线内网环境，无法访问公网 |
| 资源限制 | 单机部署，内存 ≤ 8GB |
| 安全要求 | 符合《电子渠道系统日志运维安全规范》 |

## 3. 技术选型论证

### 3.1 编程语言选型

选择 **Python 3.10**

**理由**:
1. 机器学习生态最完善（Pandas、Scikit-learn、LightGBM原生支持）
2. 开发效率高，迭代速度快
3. 团队技术栈统一，维护成本低
4. 通过Uvicorn异步框架弥补性能短板

### 3.2 机器学习框架选型
**决策**: 选择 **LightGBM**

**理由**:
1. Leaf-wise生长策略，训练速度快
2. 原生支持类别特征，无需One-Hot编码
3. 内存效率高，适合内存受限环境
4. 模型文件小，部署便利

### 3.3 Web框架选型

**决策**: 选择 **FastAPI**

**理由**:
1. 基于Starlette，性能接近Go/Node.js
2. 原生异步支持，高并发场景表现优秀
3. 基于Pydantic自动数据验证和文档生成
4. 类型提示完善，IDE支持好

### 3.4 容器化方案选型
**决策**: 选择 **Docker + Docker Compose**

**理由**:
1. 环境一致性强，解决"在我机器上能跑"问题
2. 镜像可离线导入导出，适合内网环境
3. Docker Compose编排简单，单机部署方便
4. 业界标准，文档和社区支持丰富

**文件位置**: `src/data/loader.py`

**类图设计**:

```
┌─────────────────────────────────────────────────────────┐
│                      DataLoader                          │

├─────────────────────────────────────────────────────────┤

│ + load_and_clean(file_path: str) -> pd.DataFrame        │
│ + decode_phone(text: str) -> str  [static]              │
├─────────────────────────────────────────────────────────┤
│ 内部方法:                                                │
│ - _detect_separator(file_path) -> str                   │
│ - _clean_target(df) -> pd.DataFrame                     │
│ - _clean_time(df) -> pd.DataFrame                       │
│ - _clean_numeric(df) -> pd.DataFrame                    │
│ - _map_columns(df) -> pd.DataFrame                      │
└─────────────────────────────────────────────────────────┘
```

**核心流程**:

```python
def load_and_clean(self, file_path):
    # 1. 自动检测分隔符并读取
    df = self._read_with_auto_separator(file_path)

    # 2. ID解密 (Base64 -> 明文)
    df['user_id'] = df['user_id'].apply(self.decode_phone)

    # 3. Target标签清洗 (1→1, 其他→0)
    df = self._clean_target(df)

    # 4. 时间格式转换 (YYYYMMDDHHMMSS → datetime)
    df = self._clean_time(df)

    # 5. 数值列类型转换
    df = self._clean_numeric(df)

    # 6. 英文→中文列名映射 (特征工程依赖)
    df = self._map_columns(df)

    # 7. 排序
    return df.sort_values(['user_id', 'trigger_time'])
```

**设计要点**:
- 支持逗号、制表符、竖线三种分隔符自动识别
- Base64解码失败时返回原值，保证容错
- 时间解析失败的行会被过滤
- 英文列名到中文列名的映射，兼容特征工程的历史代码

## 5. 机器学习方案

### 5.1 问题定义

| 项目 | 描述 |
|------|------|
| **任务类型** | 二分类 |
| **正样本** | 高购买意向用户 (target=1) |
| **负样本** | 低购买意向用户 (target=0) |
| **评估指标** | AUC, PR-AUC, F1-Score, KS值 |
| **业务目标** | 在商机占比≤50%约束下最大化F1 |

### 5.2 模型选择

**主模型**: LightGBM (Gradient Boosting Decision Tree)

**模型配置**:

```python
base_params = {
    'objective': 'binary',        # 二分类目标
    'metric': 'auc',              # 评估指标
```

### 5.4 阈值优化策略

**优化目标**: 在商机占比≤50%的约束下，最大化F1-Score

**算法流程**:

```
输入: y_true (真实标签), probs (预测概率)
输出: best_threshold (最优阈值)

1. 初始化 best_score = -1, best_threshold = 0.6

2. FOR threshold IN [0.30, 0.31, ..., 0.90]:
   2.1 y_pred = (probs >= threshold)
   2.2 pos_rate = mean(y_pred)

   2.3 IF pos_rate > 0.5:  # 业务约束
         CONTINUE

   2.4 f1 = F1_Score(y_true, y_pred)

   2.5 IF f1 > best_score:
         best_score = f1
         best_threshold = threshold

3. IF best_threshold未找到:
     # 兜底逻辑
     best_threshold = min(0.95, max(0.5, mean(probs) + std(probs)))

4. RETURN best_threshold
```

### 5.5 模型评估指标

| 指标 | 公式 | 业务含义 |
|------|------|----------|
| **AUC** | ROC曲线下面积 | 模型整体排序能力 |
| **PR-AUC** | PR曲线下面积 | 正样本识别能力 |
| **F1-Score** | 2×P×R/(P+R) | 准确率召回率平衡 |
| **KS值** | max\|累计正样本率-累计负样本率\| | 区分度 |
| **Precision** | TP/(TP+FP) | 商机名单准确率 |
| **Recall** | TP/(TP+FN) | 商机覆盖率 |

## 6. 特征工程方案

### 6.1 特征泄露防护

**问题**: 训练数据中包含"订单成功"事件，如果直接使用会导致特征泄露

**解决方案**:

```python
# 定义泄露事件

    'orderSuccess',        # 订单成功
    'server_orderSuccess', # 服务端订单成功
    '支付成功',             # 支付成功
    '办理成功'              # 办理成功
]

# 但保留原始target标签
user_targets = df.groupby('user_id')['target'].max()
```

**效果**: 确保模型只学习"下单前"的行为模式

### 6.2 特征弱化策略

**问题**: 某些特征（如点击购买按钮、输入验证码）与购买行为强相关，导致：
- 已购机用户这些特征值很高
- 模型过度依赖这些特征
- 对"有意向但未下单"用户预测分数偏低

**解决方案**: 对购机直接相关特征进行弱化

```python
PURCHASE_DIRECT_FEATURES = [
    'click_buy_now_cnt',      # 点击购买次数
    'step_sms_input',         # 输入验证码
    'step_sms_submit',        # 提交验证码
    'cnt_bussProcessing',     # 业务办理次数
    'process_fail_count',     # 办理失败次数
    'max_intent_level',       # 最大意图等级
    'last_intent_level',      # 最后意图等级
]

# 弱化方法: 对数变换
for col in PURCHASE_DIRECT_FEATURES:
    fe[col] = np.log1p(fe[col]) / np.log(2)
```

**弱化方法对比**:

| 方法 | 公式 | 特点 |
|------|------|------|
| log_transform | `log1p(x)/log(base)` | 降低大值影响，保留趋势 |
| sqrt_transform | `sqrt(abs(x))*sign(x)` | 更温和的压缩 |
| cap_percentile | `clip(x, upper=P90)` | 限制极端值 |
| min_max_compress | `(x-min)/(max-min)` | 归一化到[0,1] |

## 9. 部署方案

### 9.1 Docker镜像构建

**多阶段构建策略**:

```dockerfile
# 阶段1: Builder (构建环境)
FROM ubuntu:22.04 AS builder
# 安装Miniconda + 离线安装Python依赖
# 产物: /opt/my_env (完整Python环境)

# 阶段2: Production (生产环境)
FROM ubuntu:22.04 AS production
# 从builder复制Python环境
# 复制项目代码
# 配置非root用户
# 设置健康检查
```

**镜像优化**:

| 优化项 | 方法 | 效果 |
|--------|------|------|
| 多阶段构建 | 分离构建和运行环境 | 减少最终镜像大小 |
| 离线安装 | 预下载wheel包 | 支持内网环境 |
| 非root用户 | 创建appuser | 提升安全性 |
| 健康检查 | HEALTHCHECK指令 | 支持容器编排 |

### 9.2 容器编排配置

**docker-compose.yml 核心配置**:

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
      target: production
    image: terminal-intent-api:1.0.0
    container_name: terminal-intent-api

    ports:
      - "${HOST_PORT:-8000}:8000"

    environment:
      - API_KEY=${API_KEY:-dev-key}
      - WORKERS=${WORKERS:-1}
      - LOG_LEVEL=${LOG_LEVEL:-INFO}

    volumes:
      - ./models:/app/models:ro  # 模型热更新

    deploy:
      resources:
        limits:
          cpus: '2'
          memory: 2G

    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/v1/health"]
      interval: 30s
      timeout: 10s
      retries: 3

    restart: unless-stopped
```

### 9.3 部署流程

**开发环境**:

## 10. 性能优化方案

### 10.1 模型推理优化

| 优化项 | 方法 | 预期收益 |
|--------|------|----------|
| 批量预测 | 一次predict处理多条 | 减少Python调用开销 |
| 特征缓存 | 复用特征工程对象 | 减少初始化时间 |
| 类型优化 | 使用category类型 | 减少内存占用 |
| 数值精度 | float32代替float64 | 减少内存和计算 |

### 10.2 API服务优化

| 优化项 | 方法 | 预期收益 |
|--------|------|----------|
| 异步框架 | FastAPI + Uvicorn | 高并发支持 |
| 多Worker | WORKERS=CPU核数 | 提升吞吐量 |
| 连接池 | HTTP Keep-Alive | 减少连接建立开销 |
| 响应压缩 | gzip (可选) | 减少传输时间 |

### 10.3 数据处理优化

| 优化项 | 方法 | 预期收益 |
|--------|------|----------|
| 向量化计算 | Pandas groupby + apply | 比循环快10-100倍 |
| 内存映射 | 大文件分块读取 | 避免OOM |
| 惰性求值 | 减少中间DataFrame | 减少内存复制 |

### 10.4 性能基准

| 场景 | 数据量 | 预期耗时 | 内存占用 |
|------|--------|----------|----------|
| 单用户预测 | 1条记录 | < 100ms | < 100MB |
| 小批量预测 | 100条记录 | < 500ms | < 200MB |
| 标准批量预测 | 1000条记录 | < 2s | < 500MB |
| 大批量预测 | 10000条记录 | < 10s | < 1.5GB |

**日志级别**:

| 级别 | 场景 |
|------|------|

| WARNING | 需关注但不影响服务 |

### 13.2 健康检查

**检查端点**: `GET /api/v1/health`

**返回状态**:

| 状态 | 含义 | HTTP码 |
|------|------|--------|
| healthy | 服务正常，模型已加载 | 200 |
| degraded | 服务运行，模型未加载 | 200 |
| unhealthy | 服务异常 | 503 |

### 13.3 监控指标

| 指标 | 采集方式 | 告警阈值 |
|------|----------|----------|
| 服务存活 | 健康检查 | status != healthy |

| 响应时间P95 | 日志分析 | > 5s |
| 错误率 | 日志分析 | > 5% |
| 内存使用 | docker stats | > 80% |
| CPU使用 | docker stats | > 90% |

## 14. 技术风险与应对

### 14.1 技术风险矩阵

| 风险 | 概率 | 影响 | 级别 | 应对措施 |
|------|------|------|------|----------|
| 模型效果下降 | 中 | 高 | P1 | 定期回测，监控指标 |
| 特征泄露遗漏 | 低 | 高 | P1 | 代码审查，事件类型审核流程 |
| 服务不可用 | 低 | 高 | P1 | 健康检查，自动重启 |
| 内存溢出 | 中 | 中 | P2 | 资源限制，批量大小控制 |
| API Key泄露 | 低 | 高 | P2 | 环境变量，日志脱敏 |
| 数据格式变更 | 中 | 中 | P2 | 版本兼容，输入验证 |

### 14.2 容灾设计

**故障恢复**:

| 故障场景 | 检测方式 | 恢复策略 |
|----------|----------|----------|
| 容器崩溃 | 健康检查失败 | 自动重启 (restart: unless-stopped) |
| 模型加载失败 | status=degraded | 降级运行，返回503 |
| 请求超时 | 客户端超时 | 重试机制 (客户端) |
| 资源耗尽 | OOM Kill | 资源限制 + 告警 |

**备份恢复**:

```bash
# 备份模型
cp -r models/ models_backup_$(date +%Y%m%d)/

# 恢复模型
cp -r models_backup_20250801/ models/
docker-compose restart api
```
