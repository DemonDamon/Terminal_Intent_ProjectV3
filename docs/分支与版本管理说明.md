# 分支与版本管理说明

> 本文档面向项目协作成员，说明代码分支策略与版本发布流程。新人入职请先阅读。

---

## 一、分支类型与命名

| 分支类型 | 命名示例 | 用途 |
|----------|----------|------|
| 主分支 | `main` | 最新开发主线，所有功能合并目标 |
| 版本分支 | `release/0.1`、`release/0.2` | 对应已部署或待部署的现场版本 |
| 功能分支 | `feature/xxx`、`feature/用户登录` | 开发新功能，从 main 或当前版本分支拉取 |
| 修复分支 | `fix/xxx`、`hotfix/0.1-紧急修复` | 修复 bug 或紧急问题 |

---

## 二、日常开发流程

### 2.1 新功能开发

```
1. 从 main 拉取最新代码
2. 创建功能分支：git checkout -b feature/功能名
3. 在分支上开发、提交
4. 完成后发起 PR 合并到 main（或由负责人合并）
```

### 2.2 版本分支与封板

当有代码需要部署到现场时：

```
1. 从 main 创建版本分支：git checkout -b release/0.1
2. 完成测试、部署到现场
3. 封板：打 tag 标记已部署版本，如 v0.1-deployed
4. 后续新开发：从 release/0.1 创建 release/0.2，或从 main 创建 release/0.2（视现场是否基于 0.1 迭代）
```

**封板**：表示该版本已部署，代码冻结。用 `git tag v0.1-deployed` 标记，便于回溯。

---

## 三、版本迭代策略

适用于「有多个现场、各现场版本可能不同」的场景：

```
main（最新开发线）
  │
  ├── release/0.1  ← 现场 A 部署的版本
  │     └── tag: v0.1-deployed
  │
  ├── release/0.2  ← 基于 0.1 迭代，现场 B 部署
  │     └── tag: v0.2-deployed
  │
  └── release/0.3  ← 基于 0.2 或 main 继续迭代
```

**原则：**

- 若现场 B 是在现场 A 的 0.1 基础上更新，则 `release/0.2` 从 `release/0.1` 拉取
- 若现场 B 是全新部署或与 0.1 无关，可从 `main` 拉取 `release/0.2`
- 定期将各版本分支的修复合并回 `main`，保持主线不落后

## 四、常见场景

### 4.1 修已部署版本的 bug

```
1. 从对应版本分支拉修复分支：git checkout -b fix/0.1-描述 release/0.1
2. 修复、测试、合并回 release/0.1
3. 若该 bug 也存在于 0.2、0.3，需 cherry-pick 或手动同步到对应分支
4. 建议同步合并回 main，避免主线遗漏
```

### 4.2 紧急现场问题

```
1. 从该现场对应的 release/x.x 拉 hotfix 分支
2. 修复后合并回 release/x.x，重新部署
3. 打新 tag，如 v0.1.1-deployed
4. 将修复合并回 main
```

### 4.3 多人协作同一功能

```
1. 从 main 拉 feature/功能名
2. 可拆子任务：feature/功能名-子任务A、feature/功能名-子任务B
3. 各自开发完成后，依次合并到 feature/功能名
4. 功能整体完成后，合并 feature/功能名 到 main
```

## 五、操作速查

| 操作 | 命令示例 |
|------|----------|
| 拉取最新 | `git pull origin main` |
| 创建功能分支 | `git checkout -b feature/xxx main` |
| 创建版本分支 | `git checkout -b release/0.1 main` |
| 封板打 tag | `git tag v0.1-deployed` 或 `git tag -a v0.1 -m "0.1 版本部署"` |
| 推送 tag | `git push origin v0.1-deployed` |
| 查看所有 tag | `git tag -l` |

---

## 六、注意事项

1. **不要直接在 main 上开发**，始终通过分支开发后合并
2. **封板前确认**：该版本已测试、可部署，再打 tag
3. **修复要回补**：修了版本分支的 bug，记得合并回 main
4. **分支及时清理**：已合并且不再使用的分支可删除，减少干扰
